# サーバー仕様（β版）

ここでは、ObserLeaf（β版）におけるRaspberry Pi 5上のサーバー（Djangoアプリケーション）の仕様についてまとめている。


## 1. 概要

β版では、Raspberry Pi 5がWebサーバーおよびデータ管理を担当する。

サーバーは、ESP32から送信された計測データの受信・検証・保存、植物および計測デバイスの管理、デバイス設定の配布、保存した計測データのWebブラウザへの表示を行う。

本書では、サーバーの内部構成と処理仕様、および起動・運用の手順を対象とする。システム全体の構成については「システム構成（β版）」を、データモデルについては「ER図（β版）」を、APIごとのデータ項目については「データフロー（β版）」の「3. データ項目」を、データの保存方針については「データ管理方針（β版）」を参照すること。

なお、`raspberry-pi/` 直下の `sensor_app.py` および `sensor_logger.py` はα版時代のファイルであり、β版のサーバーには含まれない。


## 2. 動作環境

| 項目 | 内容 |
| --- | --- |
| サーバー | Raspberry Pi 5 |
| OS | Raspberry Pi OS |
| プログラミング言語 | Python |
| Webアプリケーションフレームワーク | Django 6.0.6 |
| アプリケーションサーバー | Gunicorn（systemdでサービス化し、長期運用） |
| データベース | SQLite（ファイル名: sensor_data.db、プロジェクト直下に配置） |
| 静的ファイル配信 | WhiteNoise |
| タイムゾーン | Asia/Tokyo |
| 言語設定 | ja |
| クライアント | PC Webブラウザ |

プロジェクトの主な設定は `plant_project/settings.py` で管理する。現在の設定では、デバッグモード（DEBUG）は有効、ALLOWED_HOSTS は全許可となっている。


## 3. プロジェクト構成

サーバーのコードは `raspberry-pi/plant_project/` に配置されている。

```
raspberry-pi/plant_project/
├─ manage.py
├─ plant_project/        プロジェクト設定（settings.py、urls.py、wsgi.py、asgi.py）
├─ dashboard/            本システムのアプリケーション
│  ├─ models/            データモデル
│  ├─ views/             画面表示とAPIの入口
│  ├─ services/          検証・変換・保存などの処理本体
│  ├─ forms.py           入力フォーム
│  ├─ admin.py           管理サイトへのモデル登録
│  ├─ templates/         画面テンプレート
│  └─ static/            CSS、JavaScript（グラフ描画など）
├─ templates/            全体共通テンプレート（base.html）
└─ static/               全体共通の静的ファイル
```

### 3.1 モジュール構成

| モジュール | 主なファイル | 役割 |
| --- | --- | --- |
| モデル | models/plants.py | 植物マスタ（PlantMaster）と育成植物（Plant）を定義する |
| モデル | models/device.py | 計測デバイス（Device）を定義する。通信状態の判定もここで行う |
| モデル | models/sensor_log.py | 計測データ（SensorLog）を定義する |
| ビュー（API） | views/api.py | ESP32向けAPIとグラフデータAPIの受付とレスポンス返却を行う |
| ビュー（画面） | views/dashboard.py | ダッシュボードの表示データ作成と生育環境の状態判定を行う |
| ビュー（画面） | views/plants.py、views/devices.py | 植物およびデバイスの一覧・詳細・作成・編集・削除を行う |
| サービス | services/sensor_service.py | 計測データ受信処理の全体を統括する |
| サービス | services/validator_service.py | 受信したJSONデータの検証を行う |
| サービス | services/device_service.py | デバイスの取得・登録・情報更新を行う |
| サービス | services/conversion_service.py | 生データから土壌水分率と光量スコアへの変換を行う |
| フォーム | forms.py | 植物フォーム（PlantForm）とデバイスフォーム（DeviceForm）を定義する。デバイス設定の変更検知と設定バージョンの更新もここで行う |

ビューはリクエストの受付とレスポンスの返却に専念し、検証・変換・保存などの処理本体はサービス層に分離している。Django REST frameworkは使用せず、通常のDjangoビューで実装している。

### 3.2 URL構成

| URL | 内容 |
| --- | --- |
| `/` | ダッシュボード |
| `/plants/` 配下 | 育成植物の一覧・詳細・作成・編集・削除 |
| `/devices/` 配下 | 計測デバイスの一覧・詳細・作成・編集・削除 |
| `/api/receive` | 計測データ受信API（ESP32向け） |
| `/api/device_config/` | デバイス設定取得API（ESP32向け） |
| `/api/device_config/applied/` | 適用済み設定報告API（ESP32向け） |
| `/api/chart-data/` | グラフデータ取得API（ブラウザ向け） |
| `/admin/` | Django管理サイト（各モデルの管理） |

各APIのデータ項目は「データフロー（β版）」の「3. データ項目」にまとめる。


## 4. 処理仕様

### 4.1 計測データ受信処理

計測データ受信APIが呼び出された場合、以下の順序で処理する。

1. リクエストボディをJSONとして読み込む
2. 検証サービスでデータの検証を行う（「4.2 検証ルール」を参照）
3. デバイスサービスでデバイスを取得する。MACアドレスをキーとして検索し、未登録の場合は新規登録する
4. timestamp（Unix時刻、秒）を計測日時（measured_at）へ変換し、受信日時（received_at）として現在時刻を付与する
5. 変換サービスで、土壌水分の生データを土壌水分率へ、光の生データを光量スコアへ変換する
6. SensorLogとして保存する
7. デバイスの最終通信日時（last_seen_at）を受信日時で更新する
8. レスポンスとして、処理結果（status）とデバイスの計測間隔（next_interval）を返す

新規登録時のデバイス名は、送信された deviceName（最大37文字）とMACアドレス（コロンを除いたもの）を組み合わせて生成する。また、新規登録時の計測間隔の初期値は300秒とする。

受信のたびに、デバイスのIPアドレス、ファームウェアバージョン、各センサーの報告された有効状態（reported_*_enabled）を最新の値へ更新する。

処理中に例外が発生した場合は、HTTPステータス400で `status`（`error`）と `message` を返す。POST以外のメソッドの場合は405を返す。

### 4.2 検証ルール

受信データの検証は、以下のルールで行う。不正なデータは例外として処理し、保存しない。

- 必須項目（12項目）がすべて存在すること
- deviceName と firmwareVersion は、空でない文字列であること
- macAddress は `XX:XX:XX:XX:XX:XX` 形式であること
- ipAddress は、有効なIPアドレスであること
- timestamp は、正の整数であること
- 各センサーの有効状態（dhtEnabled など）は、真偽値であること
- temperature と humidity は、有限の数値または null であること。また、両方とも値を持つか、両方とも null であること
- soilRaw と lightRaw は、0〜4095の整数または null であること
- 無効なセンサーの計測値は、null であること

### 4.3 データ変換

変換は変換サービスで行い、変換後の値も生データとあわせて保存する。

土壌水分率（moisture）:

- 乾燥時の生データを2550、湿潤時の生データを500として割合を算出する
- 0〜100の範囲に制限し、小数第1位までとする

光量スコア（light）:

- 暗い時の生データを4095、明るい時の生データを0として割合を算出する
- 0〜100の範囲に制限し、小数第1位までとする

生データが null の場合は、変換を行わず null のまま保存する。

### 4.4 デバイス設定の配布と適用報告

デバイス設定は、デバイスの編集画面（デバイスフォーム）で変更する。既存デバイスの編集時に、以下の設定項目のいずれかが変更された状態で保存された場合、設定バージョン（config_version）を1つ進める。

- 計測間隔（interval_seconds）
- 各センサーの希望する有効状態（desired_dht_enabled、desired_soil_enabled、desired_light_enabled）

デバイス設定取得APIは、デバイスに設定された計測間隔と希望する有効状態を、現在の設定バージョンとともに返す。

適用済み設定報告APIでは、報告内容を検証したうえで、適用済みバージョン（applied_config_version）を記録する。報告されたバージョンが配布中の設定バージョンより新しい場合は、HTTPステータス409でエラーとする。また、古い報告が遅れて届いた場合でも、記録済みの適用済みバージョンを巻き戻さない。

### 4.5 ダッシュボード表示処理

ダッシュボードでは、以下を表示する。

- 最新の計測データ（最新ログ）
- 直近20件の計測データによる時系列グラフ（温度、湿度、土壌水分率）
- 生育環境の状態判定結果とアラート（「4.6 生育環境の状態判定」を参照）

グラフ用データの作成にあたっては、温度と湿度は null の場合に直前の値を引き継ぎ（前方補完）、土壌水分率は null のまま（欠損として）扱う。

表示に使用する計測間隔は、最新ログのデバイスに設定されたものとし、計測データが存在しない場合は300秒とする。

### 4.6 生育環境の状態判定

最新の計測データについて、温度、湿度、土壌水分率の3項目を判定する。判定基準には、最新ログのデバイスに紐づく育成植物の植物マスタが持つ適正範囲（下限・上限）を使用する。光量は判定の対象としない。

| 状態 | 条件 |
| --- | --- |
| 未計測（unmeasured） | その項目の計測値がない（null） |
| 判定対象外（unconfigured） | しきい値が未設定、または植物マスタが未設定 |
| 警告（warning） | 計測値が下限を下回る、または上限を超える |
| 正常（normal） | 計測値が下限〜上限の範囲内 |

警告となった項目は、アラートとしてダッシュボードに表示する。

### 4.7 デバイスの通信状態判定

デバイスの通信状態は、最終通信日時と計測間隔から判定する。

| 状態 | 条件 |
| --- | --- |
| 未通信 | 一度も通信していない（last_seen_at が未設定） |
| 通信確認済み | 最終通信からの経過時間が、判定時間以内 |
| 通信未確認 | 最終通信からの経過時間が、判定時間を超えている |

判定時間は「計測間隔の3倍」とし、最低でも60秒とする。

## 6. 起動・運用

### 6.1 起動手順

1. Pythonの実行環境を用意し、Djangoをインストールする
2. プロジェクトのディレクトリ（`raspberry-pi/plant_project/`）へ移動する
3. データベースのマイグレーションを実行する

   ```
   python manage.py migrate
   ```

4. サービスを有効化し、起動する

   ```
   sudo systemctl enable obserleaf
   sudo systemctl start obserleaf
   ```

本サーバーは、Djangoの開発サーバー（runserver）ではなく、Gunicornにより長期運用する。Gunicornはsystemdのサービス（サービス名: obserleaf）として登録されており、Raspberry Piの起動時に自動で起動する。Gunicornの起動コマンド（`plant_project.wsgi:application` を 0.0.0.0:8000 で待ち受ける）は、サービスのユニットファイルで指定する。

ESP32側の設定（APIのURL）は、ポート8000番を前提としている。

### 6.2 サービスの操作

| 操作 | コマンド |
| --- | --- |
| 起動 | `sudo systemctl start obserleaf` |
| 停止 | `sudo systemctl stop obserleaf` |
| 再起動 | `sudo systemctl restart obserleaf` |
| 状態確認 | `sudo systemctl status obserleaf` |
| ログ確認 | `sudo journalctl -u obserleaf` |

### 6.3 運用上の注意

- 依存パッケージの一覧（requirements.txt など）は、現在のリポジトリには含まれていない。環境の再現には、インストール済みパッケージの控えを別途用意する必要がある。
- 植物マスタの登録やデータの直接確認には、Django管理サイト（`/admin/`）を使用できる。
- データベースファイル（sensor_data.db）のバックアップ方針については「データ管理方針（β版）」を参照すること。


## 7. 設計意図

### 7.1 サービス層へ処理を分離したこと

ビューの責務を受付と返却に絞り、検証・変換・保存の処理をサービス層へ分離した。これにより、受信処理の流れをサービス層のコードで追えるようにし、処理の変更が画面やAPIの入口へ影響しにくい構成とした。

### 7.2 生データと変換後の値をあわせて保存すること

土壌水分と光量については、生データ（ADC値）と変換後の値（土壌水分率、光量スコア）を両方保存する。これにより、変換の基準値を後から見直した場合でも、生データから再計算できる。

### 7.3 計測日時と受信日時を分離したこと

ESP32で計測した日時（measured_at）と、サーバーが受信した日時（received_at）を区別して記録する。これにより、通信による遅延などを確認できる構成とした。
