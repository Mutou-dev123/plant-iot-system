# データ管理方針（β版）

ここでは、ObserLeaf（β版）のデータ保存期間、グラフ表示、日別集計、育成植物とセンサーログの紐づけ、およびデータの保守・バックアップに関する検討事項についてまとめています。


## 1. データ保存方針

### 1.1 センサーログ（SensorLog）

センサーログは、短期間の環境変化を確認するための生データとして保存する。

- 保存期間：365日
- 保存期間を過ぎたログは、自動削除の対象とする。
- 日別集計が正常に完了したことを確認してから削除する。
- 日別集計に失敗した場合は、対象の生ログを削除しない。

### 1.2 日別集計データ（DailySensorSummary）

日別集計データは、長期的な環境変化の分析に利用するため、センサーログとは別に保存する。

- 保存期間：5年
- 保存期間を過ぎたデータは、自動削除する。
- 生ログの削除後も、日別集計データは保持する。


## 2. グラフ表示方針

### 2.1 表示期間

グラフの表示期間を選択できるようにし、短期間から長期間までの環境変化を確認できる構成とする。

### 2.2 表示項目

以下の測定項目をそれぞれ確認できるようにする。

- 気温
- 湿度
- 土壌水分
- 光量スコア

欠損値はゼロとして扱わない。グラフでは、前後に実測値がある欠損区間を補間して線を接続する。補間区間は実測値と区別できるように点線で表示する。

補間値は保存せず、日別集計にも使用しない。日別集計データが存在しない日には、集計値を補間して表示しない。


## 3. 日別集計方針

### 3.1 集計対象

集計日は、センサーログの計測日時（`measured_at`）を日本時間（Asia/Tokyo）に変換して決定する。受信日時（`received_at`）ではなく、計測日時を基準に集計する。

植物が設定されているログは、デバイスID・植物ID・集計日の組み合わせで集計する。

植物が未設定のログは、デバイスID・集計日の組み合わせで集計する。植物未設定のログを他のデバイスのログとまとめてはならない。

### 3.2 集計項目

各測定項目について、平均値・最大値・最小値を保存する。

| 測定項目 | 保存する集計値 |
|---|---|
| 気温 | 平均値・最大値・最小値 |
| 湿度 | 平均値・最大値・最小値 |
| 土壌水分 | 平均値・最大値・最小値 |
| 光量スコア | 平均値・最大値・最小値 |

集計対象となったログの総件数に加え、気温・湿度・土壌水分・光量それぞれの有効値件数を記録する。

各測定項目の平均値・最大値・最小値は、その項目に実測値があるログだけを対象に計算する。

作成日時と更新日時を記録する。

### 3.3 集計データの制約

- 植物が設定されている集計データは、デバイスID・植物ID・集計日の組み合わせで一意にする。
- 植物が未設定の集計データは、デバイスID・集計日の組み合わせで一意にする。
- 欠損値はゼロとして扱わず、欠損として扱う。
- 対象項目が全件欠損の場合、その項目の平均値・最大値・最小値も欠損とする。
- 集計処理を再実行しても、同じ集計対象のデータが重複して作成されない構成とする。


## 4. 育成植物とセンサーログの紐づけ

### 4.1 DeviceとPlantの関連付け

`Device.plant`は、デバイスに設定されている現在の観測対象植物として維持する。

デバイス管理画面から、管理対象の植物を変更できる仕様も維持する。

### 4.2 SensorLogへのPlantの追加

`SensorLog`に植物への外部キーを追加し、各計測データがどの育成植物に対応するかを記録する。

新しいセンサーログの保存時には、その時点で`Device`に設定されている植物を記録する。

保存済みのセンサーログについても、植物との紐づけを後から変更できる。植物別の日別集計には、`Device.plant`の現在値ではなく、各`SensorLog`に保存された植物を使用する。

センサーログの植物を変更した場合は、そのログのデバイス・集計日について、変更前と変更後の植物に関係する日別集計を再計算する。変更前の集計対象ログがなくなった場合は、不要になった集計データを削除する。

### 4.3 既存ログの取り扱い

既存のセンサーログについて、正確な植物IDを確認できない場合は未設定のままとし、推測で割り当てない。

必要に応じて、既存ログの植物との紐づけを後から変更できる。変更した場合は、該当する日別集計を再計算し、集計データが重複または不整合にならないようにする。


## 5. 自動処理・データ保守

### 5.1 日別集計処理

日別集計の日付は、日本時間（Asia/Tokyo）を基準とする。1日分の集計対象は、日本時間の午前0時から翌日の午前0時までとする。

日付が変わった後、前日のセンサーログを対象として日別集計を自動実行する。

集計済みの日付に属するセンサーログが後から保存された場合は、そのログの集計日を再集計する。再集計では既存の集計データを更新し、重複して作成しない。

集計処理の成功・失敗や処理件数を記録する。集計に失敗した場合は、対象の生ログを削除しない。

### 5.2 センサーログの自動削除

日別集計が正常に完了したことを確認したうえで、保存期間を過ぎたセンサーログを自動削除する。

集計処理と削除処理を連携させ、集計前の生データが失われることを防ぐ。

### 5.3 日別集計データの自動削除

保存期間が5年を超えた日別集計データを自動削除する。

自動処理の実行結果や処理件数を記録し、処理状況を確認できるようにする。

### 5.4 データベース容量の管理

SQLiteのデータベースファイルサイズを監視する。

データ削除後もデータベースファイルのサイズが自動的に小さくなるとは限らないため、必要に応じて容量メンテナンスを実施する。


## 6. バックアップ

データの保全性を高めるため、バックアップ機能の導入を検討する。

バックアップの実行方式や保存先などの詳細は未確定とし、以下の項目を今後の検討対象とする。

- Raspberry Pi本体やSDカードとは別の保存先へのバックアップ
- バックアップの実行頻度と保存世代数
- バックアップの実行日時や成功・失敗の記録
- バックアップ失敗時の通知・再実行方法
- バックアップデータの復元手順と定期的な復元テスト

具体的な実装方式は、利用可能な保存先や運用条件を確認した後に決定する。


## 7. SDカードの容量監視

### 7.1 容量情報の表示

Web画面から、ストレージの使用状況を確認できるようにする。

| 表示項目 | 内容 |
|---|---|
| 総容量 | SDカードの総容量 |
| 使用容量 | 使用中の容量 |
| 空き容量 | 利用可能な容量 |
| 使用率 | 総容量に対する使用容量の割合 |
| データベースサイズ | SQLiteのデータベースファイルサイズ |
| 自動管理処理の実行結果 | 集計・削除などの最終実行結果 |

### 7.2 容量不足の警告

ストレージの使用率に応じて警告を表示する機能を実装する。

使用率80％・90％を初期案とし、実際の運用状況に応じて警告閾値を調整する。


## 8. 今後決定する事項

以下の事項は、実装または運用条件を確認したうえで決定する。

- 定期処理の実行方式・実行時刻・失敗時の再試行方法
- デバイス削除時にセンサーログや日別集計データを保持するか
- バックアップの保存先・頻度・世代数・復元方法
- データベース容量メンテナンスの実施条件
