# サーバー側テスト（β版）

ここでは、Obserleaf（β版）のサーバー側テストの実行手順、対象別のファイル構成、および今後追加するテストの観点についてまとめている。


## 1. 概要

サーバー側のテストは、Raspberry Pi 5上で動作するDjangoアプリケーションを対象とする。テストファイルは`raspberry-pi/plant_project/dashboard/tests/` に配置する。

サーバーの処理仕様とURL構成については、[サーバー仕様](server-spec.md)を参照すること。


# 2. テストの実行手順

### 2.1 実行環境の準備

[セットアップ・運用手順](setup-guide.md#32-pythonパッケージの導入)の「3.2 Pythonパッケージの導入」に従って、仮想環境を有効化し、必要なパッケージを導入する。

テスト実行時は、`DJANGO_SECRET_KEY` にテスト用の値を指定する。テスト用のSQLiteデータベースはメモリ上に作成される。

### 2.2 全体実行

リポジトリルートからDjangoプロジェクトのディレクトリに移動し、テストを実行する。

```bash
cd raspberry-pi/plant_project
DJANGO_SECRET_KEY=local-test-only python manage.py test
```

### 2.3 対象を指定した実行

`dashboard` のテストを実行する場合は、`manage.py` があるディレクトリで次のコマンドを実行する。

```bash
DJANGO_SECRET_KEY=local-test-only python manage.py test dashboard.tests
```

モデルのテストのみ実行し、各テストの結果を表示する場合は、次のコマンドを実行する。

```bash
DJANGO_SECRET_KEY=local-test-only python manage.py test dashboard.tests.test_models --verbosity 2
```


## 3. テスト構成

以下のファイル名は、`dashboard/tests/` からの相対パスである。

| 対象 | ファイル | 主な確認内容 |
| --- | --- | --- |
| モデル | `test_models.py` | 日別集計結果と日別集計タスクの重複制約、デバイス削除時の連鎖削除、参照先の植物の削除保護、タスクの初期状態、通信状態の判定 |
| 計測データ受信サービス | `test_sensor_service.py` | センサーログと育成植物の紐づけ、植物が未設定の場合の記録、割当変更後の履歴保持、日本時間を基準とした日別集計タスクの作成と再登録 |
| 検証サービス | `test_validator_service.py` | 必須項目、温度・湿度の `null` の組み合わせと非有限値、生データの範囲と境界値、無効なセンサーの計測値 |
| 変換サービス | `test_conversion_service.py` | 土壌水分率と光量スコアへの変換、校正値、0〜100の範囲への制限、生データが `null` の場合の変換関数の戻り値 |
| 日別集計サービス | `test_daily_sensor_summary_service.py` | 集計値と有効値件数、再集計による更新、集計対象のセンサーログがない場合の処理 |
| デバイスフォーム | `test_forms.py` | アーカイブ済みの植物を選択肢から除外すること、計測間隔の変更時に設定バージョンを加算すること、設定項目に変更がない場合に同じバージョンを維持すること |
| ビュー（画面） | `test_views.py` | 育成植物のアーカイブと復元、デバイスとの紐づけの解除、既存のセンサーログの保持、POSTメソッドの制約 |
| 管理コマンド | `test_commands.py` | 日別集計処理の成功、失敗の記録、次回実行時の再試行 |

### 3.2 テストの追加先

- モデルの制約と判定処理は `test_models.py` に追加する。
- サービスの入力と処理結果は、対象に対応する `test_*_service.py` に追加する。
- フォームの入力検証と保存処理は `test_forms.py` に追加する。
- 画面の表示内容とフォーム送信後の応答は `test_views.py` に追加する。
- APIのHTTPステータスとJSONレスポンスを検証する場合は、`test_api.py` を新設する。
- 管理コマンドの実行結果と出力は `test_commands.py` に追加する。


## 4. 今後追加するテストの観点

| 対象 | 確認内容 | 追加先 |
| --- | --- | --- |
| デバイス設定取得API | 設定値の返却と、未登録デバイスに対するHTTPステータス404 | `test_api.py` |
| 適用済み設定報告API | 報告値と希望設定のバージョンが一致した場合の `up_to_date`、古い報告を受けた場合の保存済みバージョンの維持、希望設定を超える報告に対する409、未登録デバイスに対する404 | `test_api.py` |
| 計測データ受信API | 正常時のレスポンス、入力エラーに対する400、POST以外のメソッドに対する405 | `test_api.py` |
| グラフデータ取得API | 直近20件を計測日時の昇順で返すこと、欠損値を `null` として返すこと | `test_api.py` |
| ダッシュボードの初期表示 | 温度・湿度の欠損を直前の有効値で補うこと、有効値がまだない先頭の欠損を `null` のまま保持すること | `test_views.py` |
| 通信状態の判定 | 判定時間に最低60秒が適用される計測間隔で、最終通信から61秒後に「通信未確認」となること | `test_models.py` |
| デバイスフォーム | センサーの有効状態を変更した場合の設定バージョンの加算、複数の設定項目を同時に変更した場合も加算が1回であること | `test_forms.py` |
| センサー推移サービス | 1時間表示の10分区間、欠損区間の扱い、有効な計測が1件の区間における実測時刻、長期間表示における日別集計値の加重平均 | `test_sensor_trend_service.py` |
| 日別集計タスクの状態表示コマンド | 日本時間を基準とした当日分の除外、状態別件数と最も古い未処理日の表示、直近の失敗を最大5件表示すること | `test_commands.py` |

取得した設定が現在の設定より新しい場合に適用する処理は、ESP32側のテストで確認する。
